# Tutor Copilot — High-Level Implementation Plan

Prepared with HighGrade Planner · 1 November 2026

Deliver the complete homework-preparation journey for five invited tutors teaching adult A2–B2 English learners: assessment and evidence → explained objectives → suitable reviewed material → checked homework → tutor approval of every retained part → manual student handoff.

This is an ordinary plan prepared under a plan-only request. No application work, live-data use or pilot launch is authorized by this document. The checkout currently contains documentation and draft specifications; no application behavior is implemented or verified.

## Sources and scope

[Product Decisions](<Product Decisions.md>) owns product policy; [Architecture](Architecture.md) owns the selected design proposal. [HG-0003–0008](specs/README.md) own the draft requirements and acceptance scenarios. The [dataset contract](specs/datasets.md) defines planned evaluation cases. This plan coordinates delivery order; it does not replace those requirements.

Use one Python codebase with FastAPI/Jinja, a separate LangGraph worker, PostgreSQL/pgvector, Redis for generic query embeddings, Pydantic output schemas and Langfuse. Application records own evidence, decisions and export; graph checkpoints own execution position. Finish a small coherent block, integrate it and check its real boundary before another block depends on it.

## Work that starts early

**Evaluation:** prepare reviewed fixtures before implementing each model stage. Every gold label needs a qualified tutor; all critical items and at least 20% of ordinary items need second review, rounded up. Use synthetic learners initially. Add stage observations as their boundaries appear; stage 6 assembles the full gate rather than starting evaluation from scratch. Freeze membership, fixtures, schemas, rubrics, evaluators and model/prompt versions. The architecture names `langfuse==5.1.0` as its checked baseline; verify the current compatible release with version-matched documentation before installing and recording the lockfile.

**Privacy:** ownership, permission, minimization and safe logging begin in stages 0–1. Add deletion/expiry handling whenever a learner-linked store is introduced, including checkpoints and permitted evaluation excerpts. Stage 5 verifies the combined lifecycle. Real learner data waits for all controls and verified named processor purpose, retention and no-training terms. Production-to-gold reuse requires separate permission and anonymization review.

**Verification:** fixed clients help check local contracts/failure paths; they cannot prove model quality or external deletion. Exercise actual PostgreSQL/checkpointer, worker, API and Redis boundaries where their behavior matters, then run reviewed model experiments in an authorized environment. Record versioned inputs, outcomes, usage and sanitized failure categories. Do not log private prompts/keys, add placeholder tests or claim a simulated service proves the real integration.

## Choices that keep the implementation small

| Choice | Reason and trade-off |
| --- | --- |
| Complete homework before other jobs | Exposes evidence, material and approval problems early. Lesson planning and urgent replanning wait for equivalent coverage. |
| LangGraph waits; PostgreSQL domain records | Avoids a custom pause engine. Requires exact pause identities, replay-safe effects and reconciliation because checkpoint/domain commits are separate. |
| One web/worker codebase | Ordinary functions connect stages. Services, a broker and specialist-agent crews add coordination without a present requirement. |
| Exact search of eligible pgvector material first | Makes permission/relevance failures inspectable. Approximate indexes and rerankers wait for measured problems. |
| Redis for generic query embeddings only | Reuses provider work while fresh database retrieval reflects access/content changes. Redis remains disposable: 24-hour TTL, versioned keys, no private text, result-list cache or persistence. |
| Bounded async I/O for provider/database waits | Fits external waits without sharing database sessions across tasks. Keep dependent teaching stages sequential; use bounded threads only for blocking parsing and processes only for measured CPU work. |

## First implementation task and deferred choices

When implementation is requested, start with stage 0 and the first authenticated learner-save block in stage 1. Inspect the relevant HG-0003/0007 scenarios, choose compatible database/authentication dependencies, implement the smallest persistent operation, establish its real checks and document the verified commands. Do not scaffold the entire backlog first.

Choose named identity/model/embedding providers, compatible versions, permitted execution environment and hosting/backup arrangements when their first integration needs them. Fetch current Context7 documentation before using new framework/library features. Compare model candidates on reviewed fixtures; no quality winner, cost budget or delivery date is assumed here. Stage 7 additionally needs usable reviewed material for the cohort, operator recovery/deletion procedures and explicit launch authority.

Lesson planning, urgent replanning, live student tutoring, unrelated original authoring, MCP/email/calendar delivery, paid billing, additional agent frameworks and automatic mid-generation recovery remain outside this plan. Requirements and eventual execution evidence stay with their existing specifications.
